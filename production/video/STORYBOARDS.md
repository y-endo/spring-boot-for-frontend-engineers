# 動画の絵コンテ（監督決定版）

品質基準は `thread-model`（台本 `scripts/thread-model.json`、場面 `scripts/scenes/thread_model.py`）。必ず両方を読んでから作ること。

共通ルール:
- 45〜90秒。話者14、speed 1.2。字幕は1行あたり全角26字×2行以内。英字の読みは `voice` フィールドで指定（例：「ジャバ」「エスキューエル」）。
- コードは映さない。画面の文字は短いラベルだけ。
- 場面ごとに要素を入れ替え（pop_out）、カメラの寄り引き2〜4回、強調は pulse/shake/recolor。
- 図は y > -2.8 に配置（字幕と重ならない）。
- 冒頭は title_card（1行目の間だけ）。最後の1行は「一言まとめ」を大きく表示。
- 失敗は赤（RED）、成功は緑（GREEN）、待ちは黄（YELLOW）で統一。ただし色だけでなく形・ラベルでも区別する（✕、OK、待ち など）。
- 技術的に正しいこと（下の「正確さの注意」を厳守）。

---

## V2 `di-container`：DIコンテナ：配役表で役者をつなぐ（第11章、60〜75秒）

例え：劇団の演出家（DIコンテナ）が配役表を作り、役者（Bean）に相手役を手渡す。

1. 台本（クラス）には「相手役：PollRepository が必要」と書いてあるだけ。自分では相手を連れてこない。
2. 起動時、演出家がフォルダを巡回し、`@Component` の札が付いた役者を名簿に載せる（コンポーネントスキャン）。
3. 依存の矢印でグラフを描く（Controller → Service → Repository）。
4. 依存されている側から順に生成し、コンストラクタで相手役を手渡す（コンストラクタ注入）。
5. 全員の配役が終わったら幕が上がる＝起動完了。役者は基本1人1役で全公演に出続ける（singleton）。
6. 対比：ReactのProviderは木の中で値を渡す。Springは起動時に一括で、木ではなくグラフ。
7. 失敗例：自分で `new` した役者は名簿に載っていないので相手役がいない（null）。
8. まとめ：「必要なものは、自分で作らず、受け取る」。

正確さの注意：Beanの生成順は依存関係で決まる。singletonはアプリ全体で1つ（リクエストごとではない）。

## V3 `request-journey`：リクエストの旅（第12章、70〜85秒）

1. ブラウザから fetch。HTTPリクエストを「封筒」で描く。
2. Tomcat の入口で、スレッドプールの店員（スレッド）1人が封筒を受け取る。他の店員も別の封筒を同時に運んでいる。
3. Filter の列（例：ログ、Security）を順に通過し、各Filterでスタンプ。
4. DispatcherServlet が宛先表（HandlerMapping）を見て、該当する Controller のメソッドを選ぶ。
5. JSON本文を Jackson が Java のオブジェクト（record）に変換。`@Valid` の検問。
6. Controller → Service → Repository → DB と進み、結果が戻る。
7. 戻り値を Jackson が JSON に変換。Filter を逆順に通って戻る。
8. 同じ店員が最初から最後まで運び、終わったらプールに戻る。
9. まとめ：「1つのリクエストを、1人のスレッドが最後まで運ぶ」。

## V4 `tx-proxy`：@Transactionalと秘書（プロキシ）（第23章、75〜90秒）

例え：社長（Serviceの本体）の前に秘書（プロキシ）が立っている。

1. Controller は社長に直接ではなく、秘書に依頼する（Springが注入したのは秘書）。
2. 秘書が BEGIN → 社長が INSERT を2回 → 秘書が COMMIT。
3. 例外の場面：社長が RuntimeException を投げる → 秘書が ROLLBACK。
4. checked例外（Exception系）は、既定ではROLLBACKせずCOMMITしてしまう（ルール表示：「非検査例外→ロールバック／検査例外→既定はコミット」）。
5. 自己呼び出し：社長が自分の別メソッドを直接呼ぶと、秘書を通らない → その呼び出しの @Transactional は効かない。
6. 例外を社長が握りつぶすと、秘書は失敗に気づけず COMMIT してしまう。
7. まとめ：「@Transactional は、秘書を通ったときだけ効く」。

正確さの注意：Spring既定のロールバック規則は「RuntimeException と Error でロールバック、checked例外ではロールバックしない」。privateメソッドや自己呼び出しはプロキシを経由しない。

## V5 `connection-pool`：コネクションプール：傘が足りない（第24章、60〜75秒）

例え：貸出用の傘立て（傘＝DB接続、例として10本）。

1. リクエスト（店員）が傘を借りてDBへ行き、終わったら返す。返却されると次の人が使える。
2. 傘を作るのは時間がかかる（接続確立は高コスト）→ 最初に用意しておいて使い回す＝プール。
3. 遅いSQL（または、トランザクション中の外部API呼び出し）で傘を長く持ったままの人が出る → 傘が減る → 後ろに行列。
4. 待ちが一定時間（例：30秒）を超えると「接続取得タイムアウト」でエラー。
5. 店員（スレッド）を増やしても、仮想スレッドで安く大量に雇っても、傘の本数は増えない → 行列が長くなるだけ。
6. 対策：傘を持つ時間を短くする（遅いSQLを直す、トランザクション中に外部通信しない）、本数を測って決める。
7. まとめ：「ボトルネックは、店員ではなく傘の本数」。

正確さの注意：HikariCPの既定の最大数は10、接続取得の既定タイムアウトは30秒（数値は「例えば」として出す）。

## V6 `last-seat-race`：残り1枠に2人：競合とロック（第25章、75〜90秒）

1. 投票ルームの参加者は上限50人、現在49人。「残り1枠」。
2. 横に2本の時間レーン（参加者A、B）。
3. A と B がほぼ同時に「今何人？」（SELECT count）→ 2人とも 49 を見る → 「入れる」と判断。
4. 2人とも INSERT → 51人。上限を超えた（赤）。
5. 「トランザクションを付ければ大丈夫？」→ それだけでは防げない（両方とも自分のトランザクションの中で49を見ている）。
6. 対策：まず投票ルームの行に鍵を掛ける（SELECT ... FOR UPDATE）。A が鍵を取る。B は鍵が開くまで待つ（黄）。
7. A が数えて49 → INSERT → COMMIT で鍵が開く。B が鍵を取り、数え直すと50 → 「満員」で拒否（409）。
8. まとめ：「数えてから入れるなら、数える前に鍵を掛ける」。

正確さの注意：PostgreSQLの既定の分離レベルREAD COMMITTED。FOR UPDATE で待たされた側は、ロック取得後の文で最新のcommit済みデータを見る（だからロック後に数え直す）。

## V7 `idempotency`：応答が消えても二重登録しない（第27章、70〜85秒）

例え：宅配の伝票番号。

1. スマホ → サーバー：「選択肢を追加」。サーバーは保存に成功（DBに1行、緑）。
2. 戻りの応答が、トンネル（電波の悪い場所）で消える。
3. スマホは「失敗した」と思い、もう一度送る → サーバーはまた保存 → 2行（赤）。二重登録。
4. 対策：リクエストに伝票番号（Idempotency-Key）を付ける。
5. サーバーは番号簿を見る。初めての番号なら処理して、結果を番号簿に保存（保存と番号簿の記録は同じトランザクション）。
6. 同じ番号が再送されたら、処理せずに保存してある結果をそのまま返す → 1行のまま（緑）。
7. 同じ番号で中身が違うリクエストが来たら、エラー（422）で断る。
8. 番号簿は一定期間（例：24時間）で掃除。
9. まとめ：「再送されても、効果は1回」。

正確さの注意：「exactly once」とは言わない。保証は「番号簿の保持期間内・同じ利用者のキーの範囲で、効果の重複を防ぐ」。

## V8 `csrf-cookie`：ブラウザはCookieを自動で添える（第34章、70〜85秒）

1. 左に正規サイト（QuickVote）、右に悪意のあるサイト。中央にサーバー。
2. ブラウザは、QuickVote宛てのリクエストに、QuickVoteのCookie（入館証）を自動で添える。正直者。
3. 利用者が悪意のあるサイトを開くと、そのページが裏でQuickVote宛ての「投票を削除」リクエストを送らせる。
4. ブラウザは律儀にCookieを添えてしまう（条件次第。SameSite=Lax なら別サイトからのPOSTには付かない、を補足ラベルで）。
5. サーバーがCookieだけで本人と判断すると、削除が通ってしまう（赤）。
6. 対策：CSRFトークン。正規サイトのページだけが知っている合言葉をヘッダーに付けて送る。悪意のあるサイトは合言葉を読めないので、サーバーが拒否（403、緑の盾）。
7. CORSは別物：「他のサイトのJavaScriptが応答を読めるか」を決めるブラウザのドアマン。送信自体は止めない場合がある。
8. まとめ：「Cookieは自動で付く。だから合言葉で確かめる」。

正確さの注意：SameSite=Lax はトップレベルナビゲーションのGETには付く。CORSはサーバーを守る仕組みではない（ブラウザがレスポンスの読み取りを制限する仕組み）。

## V9 `sse-resume`：SSEの切断とLast-Event-ID（第37章、75〜90秒）

例え：ラジオ局（サーバー）とラジオ（ブラウザ）。

1. ブラウザが接続すると、イベント #41、#42 が順に届き、得票バーが伸びる。
2. トンネルで電波が切れる。その間にサーバー側では #43、#44、#45 が起きて、DBの履歴台帳に積まれる。
3. ブラウザ（EventSource）が自動で再接続。そのとき「最後に受け取ったのは #42」（Last-Event-ID: 42）を伝える。
4. サーバーは台帳から #43〜#45 を先に送り、そのあとライブ配信に合流（#46…）。
5. 重複して届くことがある（#45が2回）→ ブラウザはIDを見て2回目を無視。
6. 台帳の保存期間を過ぎていたら、差分ではなく「現在の状態をまるごと取り直す」。
7. まとめ：「切れても、台帳から続きを届ける」。

## V10 `n-plus-one`：N+1：SQLの滝（第40章、60〜75秒）

例え：レジのカゴ（永続コンテキスト）と、「あとで店員に聞く」札（Lazyロード）。

1. 「投票の一覧と、それぞれの選択肢を表示したい」。
2. まず投票一覧を1回のSQLで取得（1本）。
3. 選択肢はLazy（あとで聞く札）。ループで投票ごとに選択肢を取りに行く → 投票が100件ならSQLが100本追加。
4. 右側にSQLログが滝のように流れる演出。合計101本（1＋N）。
5. 応答時間のバーが伸びる。
6. 対策：最初から一緒に取ってくる（fetch join / 必要な形だけ取るDTO）。SQLが1〜2本に。
7. 注意：トランザクションが終わった後に札を見に行くと、エラー（LazyInitializationException）。
8. まとめ：「SQLが何本流れるか、言えるようにする」。
