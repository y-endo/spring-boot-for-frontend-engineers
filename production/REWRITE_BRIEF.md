# 文章の書き直し指示書

教材の本文（`docs/`）を、内容を変えずに読みやすい日本語へ書き直すための指示書です。
作業を始める前に、スキル `japanese-tech-writing` を Skill ツールで読み込んでください。この指示書は、そのスキルをこの教材に当てはめるときの優先順位と具体例です。

## 1. 目的

読者は、フロントエンドの実務経験があり、バックエンドを専門にしてこなかったエンジニアです。今の本文は内容は正しい一方で、次の2点が弱点になっています。

- AI が書いた文章だと一目で分かる（太字だらけ、箇条書きだらけ、短い文の羅列、どの節も同じ調子）。
- 文法は正しいが、ふだんあまり使わない硬い言葉や、比喩が多い。

書き直しで優先するのは、「日本語として正しいか」ではなく「ふだん使われている言葉で、難しい言い方をしていないか」です。IT用語と業界でふつうに使う言葉（デプロイ、ロールバック、枯渇、冪等性、レイテンシなど）はそのまま使って構いません。

## 2. 変えてはいけないもの

次は一字も変えないでください。`production/tools/check_rewrite.py` が機械的に確かめます。

- コードブロック（```で囲んだ部分。出力例・Mermaid も含む）
- 見出しの行（アンカーが変わると他の章からのリンクが切れる）
- リンク先 `](...)` の中身（リンクの表示文字は変えてよい）
- 動画カード `<div class="video-card">…</div>` と、`??? note "字幕全文"` の中身（動画の音声と一致させている）
- 注意書きの行そのもの（`!!! warning "この例えが外れる点"` のような行。中の本文は書き直してよい）

ほかに、次も変えないでください。

- 技術的な事実、数値、バージョン、手順の順番、コマンドの説明。書き直しは表現だけで、内容は足しも引きもしない。
- 誤りや古い記述を見つけても、黙って直さない。報告に書く。
- 冒頭の「この章でできるようになること」（goal-box）は箇条書きのままでよい。表の構造も変えない（セルの文章は直してよい）。

## 3. 直すこと

### 3.1 ふだんの言葉で書く

硬い書き言葉や、技術書でしか見ない言い回しを、話すときに使う言葉へ言い換えます。

| 書き直す前 | 書き直した後の例 |
| --- | --- |
| 〜を担う／〜を担保する（技術用語でない場面） | 〜を受け持つ／〜を保証する、〜を守る |
| 顕在化する | 表に出る、問題になる |
| 〜し得る | 〜することがある、〜できる |
| 〜に寄与する | 〜に役立つ |
| 〜を鑑みて | 〜を考えて |
| 看過できない | 見過ごせない |
| 〜において | 〜で |
| 〜という観点から | 〜で見ると（中身がなければ削る） |

比喩や擬人化で言っている文は、何が起きているかをそのまま書きます。

- 「DB が悲鳴を上げているわけでもありません」→「DB の負荷が高いわけでもありません」
- 「例外が握りつぶされて秘書は気づけない」のように、教材全体で決めた例え（秘書＝プロキシ、傘立て＝コネクションプールなど。`production/CURRICULUM.md` の「中心の例え」）の中で使う擬人化は残してよい。それ以外の場面で、クラスやデータが意思を持つように書かない。
- 「〜の正体」「〜という罠」「牙をむく」のような煽り気味の言葉は、見出し以外では「〜の仕組み」「〜という落とし穴」「〜で問題になる」などに直す。見出しは変えない。

### 3.2 太字を大幅に減らす

今は全体で約4600か所あります。一節に一、二か所まで、誤読を防ぎたい否定や、その節の結論だけに残します。文の中で語を目立たせたいときは、語順と文の組み立てで目立たせます。

### 3.3 箇条書きを段落に戻す

理由・因果・流れを説明している箇条書きは、接続の言葉（「そのため」「ところが」「このとき」など）でつないだ段落に書き直します。箇条書きのまま残すのは、手順、並列の項目（設定値の一覧、選択肢など）、動画の要点だけです。

書き直す前：

```text
- 客（リクエスト）は、傘を借りて外（DB）へ行き、**用が済んだら返します**。返された傘は、次の客が使います
- 傘を新しく買う（接続を新しく確立する）のは時間がかかるので、**あらかじめ用意して使い回します**。これがコネクションプールです
- 傘が全部出払うと、次の客は**返却を待ちます**。待ちすぎると諦めます（接続取得タイムアウト）
```

書き直した後：

```text
客（リクエスト）は傘を借りて外（DB）へ行き、用が済んだら返します。返された傘は次の客が使います。傘を新しく買う（接続を新しく確立する）には時間がかかるので、店はあらかじめ何本か用意しておき、それを使い回します。これがコネクションプールです。傘が全部出払っていると、次の客は返却を待つしかありません。待ちすぎると諦めて帰ります。これが接続取得のタイムアウトです。
```

### 3.4 短い文の羅列と読点の打ちすぎを直す

一文を60字以内に切りそろえた結果、短い文が並んで細切れになっています。理由や順序でつながる文は一文にまとめるか、接続の言葉でつなぎます。ただし、一文に二つ以上の主張を詰め込まないでください。

読点は意味の区切りにだけ打ちます。主語や「は」の後に毎回打たないでください。

- 「傘は、次の客が使います」→「傘は次の客が使います」
- 「QuickVote は、PostgreSQL に、保存できるようになりました」→「QuickVote は PostgreSQL に保存できるようになりました」

### 3.5 AI らしい型を崩す

スキルの「LLM っぽい表現の禁止」「演出の抑制」に加えて、この教材でよく出る次の型を直します。

- 「〜のです」で終わる文の多用。事実を述べるだけなら「〜です」で足ります。
- 「AではなくB」の対句。根拠のない対比なら普通の文にする。
- 「ここが大事」「ポイントは〜」「重要なのは〜」の前置き。主張をそのまま書く。
- 「この章では〜します」「〜を見ていきます」の予告が節ごとに入っているもの。章の冒頭に一度あれば十分です。
- 段落の終わりに置かれた、直前の内容をくり返すだけのまとめの一文。
- イ形容詞＋「です」（「難しいです」「多いです」）。前後の文ごと書き直す。
- 読者への呼びかけ「あなた」。必要なところ以外は「読者」と書くか、主語を省く。

### 3.6 同じ調子を続けない

どの節も「問い→例え→箇条書き→注意書き」の同じ流れで書かれていると、読み手は機械的な印象を受けます。節の役割（場面の導入、仕組みの説明、手順、結果の読み方）に合わせて、段落の長さと書き出しを変えてください。ただし、見出しと注意書きの構成は変えないでください。

## 4. 作業の手順

1. 担当ファイルを最初から最後まで読む。
2. 節ごとに書き直す。Edit ツールで節単位に置き換えるのが安全です。
3. ファイルごとに次を実行し、`[OK]` になるまで直す。

```bash
.venv/Scripts/python production/tools/check_rewrite.py docs/partNN/xxx.md
```

4. 書き直した文章を読み返し、3章の項目が残っていないかを確認する。太字の残り数は次で数えられます。

```bash
grep -o '\*\*' docs/partNN/xxx.md | wc -l
```

5. 担当ファイルを全部終えたら、次でビルドが通ることを確かめる。

```bash
.venv/Scripts/mkdocs build --strict
```

## 5. 報告

作業の最後に、次を日本語で短く報告してください。

- 書き直したファイルと、各ファイルの太字の数（前→後）
- 内容の誤りや、古い記述に気付いたところ（直していないもの）
- 判断に迷って、そのままにしたところ
