提案の中心は、**「JavaとSpringを覚える教材」ではなく、「サーバーが守るべき約束を決め、実装し、壊して検証する教材」**にすることです。

構成は全45章。通しの題材には、**期間限定ワークショップの参加・整理券受付システム**を推します。SQLとトランザクションを先に理解し、その後にJPAの便利さと注意点を学びます。テスト、認可、運用は最終盤の付け足しにせず、段階的に導入します。

以下は教材そのものではなく、監督との議論に向けた設計案です。

**1. 全体構成：9部・45章**

45章にする理由は、言語・HTTP・永続化だけでなく、認可、並行処理、再送、通知、運用をそれぞれ独立した学習対象にするためです。ただし、1章を同じ長さにはしません。導入章は短く、競合や復旧の実験章には十分な時間を取ります。

各章のゴールは「説明できる」だけで終わらず、確認可能な成果を含めます。

**Part 4：同時に動いても壊れない更新――第16〜20章**

| 章 | 内容・見せ方 | 読み終えたらできること |
|---|---|---|
| **第16章：トランザクションの境界を決める** | 参加者登録と関連更新の途中で例外を発生させる。まずSQLのBEGIN／COMMIT／ROLLBACKを観察し、`@Transactional`へ進む。 | 「全部成功か、全部取り消しか」を決め、業務操作単位にトランザクション境界を置ける。 |
| **第17章：`@Transactional`が効く条件** | プロキシ、自己呼び出し、例外によるrollback、例外の握りつぶし、伝播、別スレッドへの処理移動。 | アノテーションの見た目で判断せず、実際の開始・commit・rollbackをテストとログで確認できる。 |
| **第18章：スレッドとコネクションプール** | 複数リクエストが同じServiceを通る様子、DB接続待ち、共有状態の競合を可視化。仮想スレッドの位置づけも扱う。 | スレッド数、接続数、DB処理能力を区別し、待ち時間や共有状態による不具合を診断できる。 |
| **第19章：定員超過を実際に起こして防ぐ** | 2接続で「残り1枠」を同時取得。開催回の親行ロック、ロック取得後の再判定、条件付きUPDATEを比較する。 | READ COMMITTEDで定員を守る更新手順を実装し、すべての更新経路が同じ規則に従う必要性を説明できる。 |
| **第20章：競合への別解と並行性テスト** | 楽観ロック、分離レベル、Serializable、デッドロック、ロック順序、有限回の再試行。Latch等で競合順序を作る。 | ロック方式を条件に応じて選び、複数接続のテストで上限・競合・再試行を検証できる。 |

トランザクションと排他制御を同じ意味で教えないことが重要です。PostgreSQLのREAD COMMITTEDでは、同じトランザクション内でも文ごとに見えるデータが変わり得ます。その挙動を2つのSQLセッションで観察させます。[PostgreSQL公式：Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

また、Springの標準的なプロキシ方式では自己呼び出しがトランザクションの助言を通らず、標準のrollback条件にも例外の種類による違いがあります。第17章はこの「覚えていないと事故になる」箇所を実験で扱います。[Spring公式：Using `@Transactional`](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

**採用する技術方針**

| 項目 | 提案 | 理由・教え方 |
|---|---|---|
| Java | Java 25。プレビュー機能は本編で使わない | 言語の新しさと実務上の再現性を両立する。新構文の網羅はしない。 |
| Spring | Boot 4.1.2を教材の基準とし、依存は原則Bootの管理に従う | Framework、Security、Jacksonを学習者が個別に組み合わせる負担を避ける。 |
| Web | Spring MVC | ブロッキングなDBアクセス、トランザクション、スレッドの関係を追いやすい。 |
| ビルド | **Maven＋Wrapper** | XMLの記述量より、標準的なライフサイクルと依存管理の見通しを優先。別のDSL学習を増やさない。 |
| Gradle | 第2章の補足と付録で読み方を扱う | `dependencies`、plugin、task、toolchain、BOMとMavenの対応を示す。二重運用はしない。 |
| IDE | **VS Codeを本編の推奨** | 学習者の既存環境との連続性を優先。Java拡張による補完・デバッグ・テストを使い、CLIでも再現できるようにする。 |

| DB | PostgreSQL。教材リリース単位でバージョン固定 | ローカル、CI、Testcontainersで同じ系統を使い、方言差を避ける。 |

**2. 通しの題材：候補と推奨**

| 候補 | 自然に扱える論点 | 教材上の難しさ |
|---|---|---|
| **期間限定ワークショップの参加・整理券受付** | 匿名参加、招待、定員、整理券発行上限、二重発行防止、呼び出しSSE、締切、期限後削除 | 主催者権限と参加者権限を明確に設計する必要がある |
| **期間限定イベントの投票・集計** | 匿名参加、参加招待、投票上限、冪等性、締切、リアルタイム集計 | 「匿名主体が別セッションを作るとどうするか」が前面に出やすい。投票の秘密性まで求めると広がる |

**推奨は「期間限定ワークショップの参加・整理券受付」です。**

利用者は、招待を受けて開催回へ参加し、その中で体験の整理券を取得します。主催者は整理券を順番に呼び出します。

データの中心は自由入力の文章ではなく、**参加資格、受付枠、整理券、状態遷移**です。卒業対象の論点を、異なる業務として学べます。

最初の仕様は次の程度に絞ります。

- 開催回の主催者は1主体。
- 有効な参加者は最大12人。
- 整理券の発行総数は開催回ごとに最大100件。
- 参加者が同時に保持できる有効な整理券は1件。
- 備考は短文のみ。文字数とUTF-8バイト数の上限を別々に定義。
- 参加締切、整理券発行締切、データ削除予定時刻を区別。
- 主催者が整理券を「待機→呼出中→完了」に進める。
- 取消済みの整理券も発行総数には含める、と最初に定義する。

最後の規則は小さいようで重要です。「上限100件」が現在の有効件数なのか、累積の発行数なのかで、実装もテストも変わります。

**段階ごとの育て方**

| 段階 | アプリの状態 |

| 第1〜10章 | メモリ上で開催回と整理券を扱う。提供されたテスト用主体を使うローカル実験。 |
| 第11〜15章 | PostgreSQLへ保存し、再起動しても状態が残る。 |
| 第16〜20章 | 同時参加・同時発行でも上限を守る。 |
| 第21〜25章 | 本物の匿名セッション、主催者／参加者認可、招待、試行制限を導入。 |
| 第26〜30章 | 再送、期限、削除ジョブ、部分的な失敗に対応。 |
| 第31〜35章 | 一部をJPAで比較実装し、設計判断を練習。 |
| 第36〜40章 | 呼び出し通知、再接続、履歴復元、2台構成。 |
| 第41〜45章 | パッケージング、観測、負荷試験、復旧、卒業変更課題。 |

認可完成前の実装は、ローカル実験用であることをページと実行プロファイルで明示します。公開手順は完成後に扱います。

**認可の設計例**

| 操作 | 非参加者 | 参加者 | 主催者 |
|---|---:|---:|---:|
| 有効な招待の引換 | 可 | 条件付き | 条件付き |
| 自分の整理券取得・取消 | 不可 | 可 | 参加資格がある場合 |
| 他人の整理券の詳細取得 | 不可 | 不可 | 可 |

**匿名利用について教える限界**

匿名主体は「同じブラウザの資格情報を持つ利用者」を識別するものであり、実在する一人の人間の証明ではありません。

したがって、

- Cookieを失うと継続利用できなくなる場合がある。
- 新しい匿名主体を作れるため、主体別制限だけでは不正を防げない。
- Cookie窃取や共有端末のリスクがある。
- 本人確認をしない以上、復旧時に確認できることにも限界がある。

という仕様上の帰結まで扱います。

**3. 各章の学習設計の型**

共通化するのはページの見出し順ではなく、**学習者が出す証拠**です。

全章で、次の4点を揃えます。

1. **判断する対象**：何を決める章なのか。
2. **観測する対象**：HTTP、SQL、DB状態、ログなど、何を見るのか。
3. **守る条件**：成功・失敗を何で判定するのか。
4. **学習者の成果**：コード、テスト、図、設計理由のいずれか。

標準的な1章の流れは次のとおりです。

| 段階 | 内容 |
|---|---|
| 導入の問い | 「定員チェックを書いたのに、なぜ13人入れたのか」など、判断したくなる具体的な問題 |
| 予測 | 実行前に結果を選ぶ。既存知識による誤解を表面化させる |
| 最小実験 | 問題に必要なコードやSQLだけで現象を見る |
| 説明 | その概念に合う文章、図、動画を選ぶ |
| 実装 | 主アプリへ組み込む。差分と完成コードを往復できるようにする |
| 壊す | 別タブ、別セッション、同時実行、切断、時刻変更などで前提を崩す |
| 証拠を残す | テスト結果、DB状態、観測値を確認する |
| 適用範囲を述べる | この実装で保証できることと、別の仕組みが必要な条件を説明する |
| 演習 | 条件を1つ変え、丸写しでは解けない課題にする |

**固定化を避ける3種類の章**

- **現象から入る章**：並行性、冪等性、N+1。先に壊れ方を見せる。
- **設計から入る章**：認可、API契約、期限。まず仕様表を作る。
- **調査から入る章**：ログ、性能、復旧。障害報告と観測結果から原因を絞る。

すべての章に例え話と動画を置く必要はありません。DDLと制約の対応は表、競合は動画、依存関係は静止図の方が適しています。

**第19章の具体例**

導入は「残り1枠なのに、2人とも201になった」です。

1. 二つのDB接続で参加者数を取得し、両方が11件を見る。
2. 両方が参加者をINSERTし、13件になる。
3. 「トランザクションを付けるだけ」で解決するか予想する。
4. 開催回の親行をロックしてから人数を再確認する。
5. 片方がcommitした後、もう片方が12件を見て拒否する。
6. ロックを取得しない別の登録経路を追加すると破れることを確認する。
7. 演習で、参加取消と新規参加が同時に起きる場合を検証する。

到達点は「`FOR UPDATE`を知っている」ではなく、**何をロックし、どの経路が同じルールに従い、どの順序で判定するか説明できること**です。

**MkDocsでの表現ルール**

| 機能 | 用途 |
|---|---|
| admonition | 「この時点の保証」「よくある誤解」「ローカル実験限定」など、意味を固定した少数の種類に限定 |
| タブ | Windows／macOS、SQL／観測結果など、比較や環境差に使う。必修説明を隠さない |
| コード注釈 | 「この行を消すと何が壊れるか」「この値の出所はどこか」を説明 |
| 折りたたみ | 演習の段階的ヒント、解答、補足。重要な前提条件は折りたたまない |
| Mermaid | 処理経路、状態遷移、ER図。コード変更と同期しやすい図 |
| SVG | スレッド、接続プール、信頼境界など、配置に意味がある図 |
| 用語集 | 定義だけでなく、初出章、実験、誤解例へリンク |

専門用語は、その場で例えば次のように定義します。

> 冪等性：同じ操作を繰り返し受け付けても、意図した効果が重複しない性質。この章では「整理券が1枚だけ発行される」ことを確認する。

例え話には、必ず「対応するところ」と「対応しないところ」を添えます。DIとReact Contextなら、「依存する値を外から受け取る点」は対応しますが、Beanの寿命や共有範囲はReactの再レンダリングモデルと異なります。

| **14. SSEが再接続すれば、抜けたイベントも自動で戻ると思う** | 第36章の最小実装で取りこぼさせ、第37・38章で履歴とカーソルを実装する。 |
| **15. 自動テストが全部緑なら本番でも保証できると思う** | 第15・30・40章で、モック、単一接続、ブラウザを通さないテストが見逃す問題を示す。保証範囲を言語化させる。 |

**7. プロとして通用する水準の線引き**

この教材で目指すのは、**小〜中規模のWebサービスについて、バックエンドの設計・実装・検証・運用を担当し、未知の問題を調査できる水準**です。

「どんな規模・業種のシステムでも一人で安全に作れる」とは約束しません。ただし、その限定を理由に実務で必須の論点を削ることもしません。

| 領域 | 卒業時に必要な水準 |
|---|---|
| Java | 型、例外、コレクション、ジェネリクス、`equals/hashCode`、不変性、リソース解放をレビューできる |
| 数値・日時 | `BigDecimal`の丸めと比較、タイムゾーン、日時の保存・表示、境界時刻をテストできる |
| API | DTO、入力制限、エラー契約、ページング、互換性、再送時の挙動を設計できる |
| SQL | JOIN、集計、制約、パラメータ化、インデックス、実行計画を読める |
| JPA | 永続化コンテキスト、flush、N+1、取得戦略、楽観ロック、OSIVの影響を説明できる |
| トランザクション | 境界、rollback条件、プロキシ、外部通信との分離、別スレッドの扱いを判断できる |
| 同時実行 | 定員や件数上限を、複数接続・複数台でも守る根拠を示せる |
| 認可 | 主体・対象・操作で判定し、他人のID指定、権限剥奪、SSE経由の漏えいを検証できる |
| ブラウザ境界 | Cookie、CSRF、CORS、HTTPS、キャッシュ、秘密情報のURL混入を扱える |
| 冪等性 | 同時再送、異なる入力でのキー再利用、結果保持期限、権限失効後の再送まで仕様化できる |
| 非同期通知 | 保存と通知の不一致、再送による重複、順序、履歴保持、再同期を説明できる |
| テスト | 単体、HTTP、実DB、並行性、実ブラウザの役割を区別し、必要な層で検証できる |
| 運用 | ログ・メトリクス、負荷制限、秘密情報、バックアップ復元、依存更新を実施できる |
| 変更 | DBマイグレーションとAPI互換性を考え、既存データを持つ環境を更新できる |
| AIレビュー | 生成コードの前提を列挙し、正常系以外の反例を作り、修正の正しさを検証できる |

特に、次の細部は省略しない方針を推します。

**上限と認可は「確認した後」の競合まで扱う**

参加資格を読んでから整理券を作る間に、主催者が参加資格を失効させる可能性があります。

教材ではまず、対象の開催回を共通のロック対象にするなど、説明しやすい規則を採用します。参加・取消・失効・整理券発行の各経路が同じ規則に従うことを確認します。高度な最適化は、測定して必要になった場合の検討に回します。

**冪等性は保存済みレスポンスを返すだけではない**

少なくとも次を扱います。

- キーを主体・操作・対象のどの範囲で一意にするか。
- 同じキーに異なる入力が来たらどうするか。
- 同時に同じキーが来たらどうするか。
- 業務更新と冪等性記録を同じトランザクションにする。
- 権限剥奪後に過去の応答を返して情報漏えいしない。
- 保持期限を過ぎた再送は、重複防止を保証できない場合がある。

「exactly once」という言葉で保証を広く見せず、**どの期間・どのスコープで重複した効果を防ぐか**を説明させます。

**SSEのイベントIDは、単なる連番で済ませない**

DBのシーケンスによる番号付与順と、トランザクションのcommit順は一致するとは限りません。大きいIDまで読んだからといって、それより小さい未commitのイベントが存在しないとは限りません。

本編では、開催回単位のロック下でイベント番号を採番し、業務更新と同時に保存する方式を採用します。配信範囲を開催回単位に揃え、順序の根拠を明確にします。

履歴からの配信を正とし、メモリ内通知は配送を早める補助にする構成なら、学習の初期段階で専用メッセージ基盤を必須にせず、再接続や複数台を検証できます。その代わり、ポーリング頻度・クエリ数・接続数の限界を第43章で測ります。

**ログは最初から許可した項目だけ残す**

リクエスト全体を記録して後からマスクする方式を基本にしません。

保存する項目は、操作名、結果分類、request ID、処理時間などから始めます。Cookie、招待秘密、短いコード、備考本文は出力しません。セキュリティ監査用の記録も、目的と保持期間を明確にします。

**本編の必修にはしないもの**

Kubernetesの運用、Kafkaクラスタ構築、複数リージョン整合性、高度なGC調整、OAuth/OIDCプロバイダ構築、決済処理は、本編の完成条件にはしません。

ただし、「必要になったら何を調べ、どこから専門知識が必要になるか」は最終部に地図として示します。

**8. 演習と到達確認**

演習は、各章の小課題、各部末の統合課題、卒業課題の3段階にします。

各部末では、**動くもの・失敗を検出するテスト・設計理由**をセットで提出させます。

| 部 | 部末課題 | 合格の証拠 |
|---|---|---|
| **Part 1** | Springなしで整理券の状態遷移と入力条件を実装 | 不正な遷移、境界値、等価性のテストがあり、例外の意味を説明できる |
| **Part 2** | 整理券発行APIとエラー契約を作る | 正常・入力不正・存在しない対象のHTTPテスト。JSONとJava型の対応を説明できる |
| **Part 3** | DBを空から構築し、一覧・保存APIを動かす | FlywayとTestcontainersで再現でき、制約違反と主要検索の実行計画を確認している |
| **Part 4** | 残り1枠へ20件の参加要求を同時実行 | 成功1件、残りは仕様どおりの拒否。上限・重複・途中状態をDBで確認できる |
| **Part 5** | 他人の開催回・整理券へアクセスを試みる | 非参加者、他参加者、失効済み主体の認可テスト。招待の同時引換でも参加は1件 |
| **Part 6** | 保存成功後に応答を失わせ、同じキーで再送 | 整理券と履歴が1組だけ存在し、結果が契約どおり。締切境界と削除停止中も正しく動く |
| **Part 7** | N+1やトランザクション不備のあるJPA実装を修正 | 修正前後のSQL数、取得結果、競合テスト、採用理由を示せる |
| **Part 8** | 2台構成でSSE接続先と更新先を分ける | 切断中の履歴復元、重複処理、権限失効、履歴切れの再同期を確認できる |
| **Part 9** | クリーン環境へ配置し、障害から復旧 | 起動・更新・バックアップ復元・調査手順を別の人が再現できる |

**並行性テストの設計方針**

「100回実行してたまたま失敗しなかった」を合格根拠にしません。

- 別のDB接続、別のトランザクションを使う。
- LatchやBarrierなどで、狙った競合位置を作る。
- 成功数だけでなく、失敗の分類と最終DB状態を見る。
- 制約違反の例外を握りつぶしていないか確認する。
- テスト用の外側トランザクションがcommitや可視性を隠さないようにする。
- すべての待機に上限を設け、テストが永久に止まらないようにする。

**到達確認は4段階**

| 段階 | 判定 |
|---|---|
| 1. 再現できる | 教材どおりの手順で動かせる |
| 2. 説明できる | コードの各境界と、失敗時の挙動を説明できる |
| 3. 検証できる | 別条件や反例を作り、保証が保たれるか確認できる |
| 4. 変更できる | 未見の仕様変更へ対応し、既存の保証を維持できる |

部末の最低条件は3、卒業条件は主要領域で4です。

**AIの使い方も段階化する**

- 最初に、学習者が仕様とテスト観点を書く。
- 次に、AIへ実装またはテスト作成を依頼する。
- 生成物に含まれる前提と未検証事項を指摘する。
- 学習者が反例を追加する。
- 最後に「なぜこの実装で守れるのか」を自分の言葉で説明する。

AIなしで長いコードを暗記して書かせる必要はありません。一方、AI生成物を読み上げるだけでは合格にしません。

**卒業課題の具体例**

次のような変更を組み合わせて渡します。

> 主催者が参加者を失効させると、以後の整理券取得と通知閲覧を拒否する。既存の整理券の扱いも決める。失効と同時の発行、発行成功後の再送、接続済みSSE、過去履歴の再取得を考慮すること。

提出物は次の5点です。

1. 仕様と権限表。
2. 実装差分とマイグレーション。
3. 正常・異常・競合のテスト。
4. 観測方法と障害時の手順。
5. 採用案、却下案、残る制約を記した短い設計記録。

追加で、通し題材とは異なる小さな予約・受付業務の設計問題を出します。名称だけを置き換えた実装から離れ、原理を転用できるか確認します。

**9. 監督への懸念・提案**

**第一に、目標は妥当ですが、短期の入門教材の分量には収まりません。**

企画段階の見積もりとして、本文・実験・部末課題で180〜260時間、卒業課題と補修で40〜80時間、合計220〜340時間程度を見込みます。これは実測前の仮置きです。

対象者のFE経験を生かして一般的な開発説明を削れても、トランザクションや認可の実験時間は削らない方がよいです。章数を減らすより、短い節へ分割して再開しやすくします。

**第二に、「まずCRUDを完成させ、最後に安全にする」という説明にしない方がよいです。**

認可の実装は第21章からですが、主体と権限の問いは第1章から示します。テストは第5章、入力制約は第9章、DB制約は第11章から必須です。

前半で一時的に保証していない事項は、各章の「この時点の保証」に表示します。完成前のコードを、そのまま公開してよいコードとして見せません。

**第三に、SQL主線とJPA後半を支持します。**

JPAから始めると、Java、Spring、SQL、ORM、トランザクションが同時に未知になります。

SQLで保存と競合を理解した後なら、JPAの説明を「便利な自動生成」ではなく、**既に知っているDB操作をどのように抽象化しているか**として進められます。逆に、SQLだけで終えると既存のSpring案件を読む力が不足するため、JPAの実習も必修です。

**第四に、匿名主体の設計を「自作認証フレームワーク」の演習にしないこと。**

セッションの生成・保存・Cookie制御などは既存の仕組みに乗せます。学習者が設計すべき中心は、主体と参加関係、招待による権限付与、対象リソースの認可です。

主催者も匿名主体である場合、Cookie喪失時の復旧をどう扱うかは必ず仕様化します。復旧機能を持たないなら、その限界をUIと説明に反映します。

**第五に、SSEは実装の段階を明確に分けます。**

1. 接続してイベントを受け取る。
2. 保存済み履歴から再接続を回復する。
3. 複数台とプロキシを含めて検証する。

この3段階を混ぜると、最初の実装が急に大きくなります。一方で、段階1のコードだけを完成形として残すのも避けます。

本編の完成構成は、PostgreSQLの履歴を正として2台で動かすところまで。専用の配送基盤は、実測した負荷や遅延要求から必要性を判断する発展課題にします。

**第六に、バージョンは教材のリリース単位で固定します。**

記録するのは少なくとも次です。

- JDKのディストリビューションと更新版。
- Bootのバージョン。
- Maven Wrapperのバージョン。
- 解決された主要依存。
- PostgreSQL、コンテナイメージ。
- Testcontainers、JUnit。
- MkDocs、Material、図の生成環境。
- 検証日とCI結果。

FrameworkやSecurityを、名前の世代だけ合わせて独立に更新しません。

Jakarta EE 11も、全仕様を学ぶという意味にはしません。本編で使うServlet、Validation、Persistenceなどに絞り、Bootアプリの構成とJakarta EE全体を区別します。

Jackson 2時代のコードや古いSpringの例を読む補足では、「古いコードは全部同じ規則で置換できる」と教えないようにします。パッケージ、設定、テスト支援の差を、実際にビルドして確認する姿勢を教えます。

**第七に、JUnit 5指定は制作前に依頼書へ反映しておくべきです。**

本案では、Boot 4.1.2の依存管理に合わせたJUnit 6を実行基盤として提案しました。依頼の狙いが「Jupiterによる現代的なJavaテストを学ぶこと」なら、その意図を保てます。

バージョン番号だけを維持するための依存上書きは、教材の再現性を損ねる可能性があります。これは監督判断として明文化したい点です。

**第八に、文章より先に、難所の実験を試作することを提案します。**

制作の先行対象は次の4つです。

- 第19章：定員競合。
- 第23章：招待の同時引換。
- 第26章：応答喪失後の冪等な再送。
- 第38章：SSEの履歴復元。

ここが理解しやすく作れれば、教材の核は成立します。動画は実験の入出力が確定してから作り、映像とコードが別の仕組みを説明してしまう事態を避けます。

**第九に、コードと本文の一致を自動検証します。**

章ごとに開始時点と完成時点を用意し、本文のコードは可能な範囲で検証済みソースから取り込みます。

CIでは、ビルド、主要テスト、空DBからの構築、旧スキーマからの更新、ドキュメント内リンクを確認します。公開前には実ブラウザでCookie・CSRF・SSEを検証します。セキュリティ上の重要な注意は、検索で途中の章だけに着地しても見える位置に置きます。

**最後に、卒業の評価軸は機能数ではなく、保証の説明と証拠に置きます。**

監督と最初に合意したい合格文は、次です。

> 学習者は、データ・権限・期限・同時実行について守る条件を定義し、Java/Springで実装し、再送や障害を含むテストで確かめ、運用時に異常を発見して復旧する方法を説明できる。AIの生成物についても、同じ基準でレビューできる。
