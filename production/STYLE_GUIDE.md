# 執筆スタイルガイド（全章共通）

この教材の執筆者（人間・AIとも）は、書き始める前に必ずこのガイドを全部読むこと。

## 0. 読者像

- フロントエンドを12年以上やってきたエンジニア。React / TypeScript / HTTP / Git / SQLの基本は分かる。
- Java・Spring・サーバーサイド特有の考え方は初めて。
- 説明しなくてよいもの：変数、関数、配列、if、ループ、DBとは何か、HTTPメソッド、JSON、Git操作。
- 必ず説明するもの：Java・Spring・サーバー特有の用語（初出時）。例：JVM、Bean、DI、トランザクション、スレッド、コネクションプール、ORM、プロキシ、アノテーション、冪等性 など。
- ゴールは「AIが書いたSpringコードを読み、レビューし、異常時の挙動を説明・検証できる」こと。暗記ではなく理解。

## 1. 文体

文章の規範はグローバルのスキル `japanese-tech-writing` に従う。そのうえで、この教材では次を優先する。書き直しの具体的な手順と例は `production/REWRITE_BRIEF.md` にある。

- です・ます調。
- 日本語として正しいかより、ふだん使われている言葉で書けているかを重視する。IT用語や業界でふつうに使う言葉はそのまま使ってよい。硬い書き言葉（「〜を担う」「顕在化する」「〜し得る」など）は言い換える。
- 短い文を並べるだけにしない。理由や順序でつながる内容は、接続の言葉を使って一つの段落として流れるように書く。
- 読点は意味の区切りにだけ打つ。主語や「は」のたびに打たない。
- 太字は一節に一、二箇所まで。箇条書きは、手順や並列の項目に限り、理由の説明は段落で書く。
- 誇張・煽り（「最強」「神」「絶対」）や、決め台詞の独立段落は使わない。
- 断定できないことは断定しない。バージョン依存の話は「Spring Boot 4.1時点では」のように書く。

## 3. 章の組み立て

章の「型」は固定しない。ただし次の要素から、その章に合うものを選ぶ。

- **この章でできるようになること**（冒頭、箇条書き3〜5個。必須）
- **問いかけ**：読者が「確かに、どうなるんだろう」と思う具体的な場面から入る
- **例え話**：抽象概念にだけ使う。例えは1つに絞り、どこまで当てはまってどこから外れるかも書く
- **フロントエンドとの対比**：React/TypeScript/ブラウザの知識で「似ている点」と「違う点」を両方書く
- **図**：構造・流れ・状態変化は文章より図
- **コード**：最小で動くもの。読む順番を示す
- **動かしてみる**：実行コマンドと、期待される出力
- **壊してみる**：わざと間違えて、エラーや異常な挙動を観察する
- **現場ではこうする**：プロとしての判断基準・アンチパターン
- **まとめ**（必須）
- **確認問題・演習**（必須。答えは折りたたみ `??? success "解答"` で）

### 毎回の判断（重要）

概念ごとに「テキスト・図・動画・コード実行のどれが一番わかるか」を判断して選ぶ。

- 時間とともに動く・順番が肝心（リクエストの流れ、並行実行の競合、トランザクションのロールバック）→ 動画またはシーケンス図
- 構造・関係（レイヤー構成、テーブル関係、クラス関係）→ 静止図
- 細かい規則・比較 → 表
- 手を動かすと一発でわかるもの → 「動かしてみる」「壊してみる」
- 同じ章で同じ種類の図を3つ以上続けない。

## 4. MkDocsの記法

### 注意書き（admonition）

```markdown
!!! note "用語：Bean（ビーン）"
    Springが生成・管理するオブジェクトのことです。...

!!! tip "フロントエンドで例えると"
    ...

!!! warning "よくある間違い"
    ...

!!! danger "本番で事故になるパターン"
    ...

!!! example "動かしてみる"
    ...

??? question "確認問題1：..."
    ...

??? success "解答"
    ...
```

用語の初出時は `!!! note "用語：○○"` で2〜4行の解説を入れる。同じ用語の2回目以降は解説しない（必要なら用語集へリンク）。

### コード

- 言語を必ず指定（```java、```sql、```bash、```yaml、```kotlin）。
- ファイルパスはタイトルで示す：```java title="src/main/java/com/example/board/BoardController.java"
- 重要行はハイライト：```java hl_lines="3 5"
- 行ごとの解説にはコード注釈を使う：コード内に `// (1)!` を書き、コードブロック直後に番号付きリストで解説。
- 1つのコードブロックは原則40行まで。長いときは分ける。
- import文は、初出のときと紛らわしいとき（Jacksonなど）だけ書く。

### タブ（比較に使う）

```markdown
=== "TypeScript（Express）"
    ```ts
    ...
    ```
=== "Java（Spring）"
    ```java
    ...
    ```
```

### 図

- 流れ・状態・関係：Mermaid（```mermaid）。ノード文字は日本語でよい。1図あたりノード15個まで。
- Mermaidで表現しにくい概念図：`docs/assets/diagrams/` のSVGを `![説明](../assets/diagrams/xxx.svg)` で貼る。
- 動画：`docs/assets/videos/xxx.mp4` を次の形で埋め込む。

```html
<div class="video-card">
  <video controls preload="metadata" poster="../../assets/videos/xxx.jpg">
    <source src="../../assets/videos/xxx.mp4" type="video/mp4">
  </video>
  <p class="video-caption">▶ 60秒でわかる：○○</p>
</div>
```

（パスは章のディレクトリ階層に合わせて調整すること）

## 5. 例え話のルール

- 例え話は「わかった気にさせる」危険がある。必ず「この例えが外れる点」を一言添える。
- 教材全体で使う中心的な例え（シリーズで統一）：
  - `CURRICULUM.md` の「中心の例え」表に従う（レストラン、店員＝スレッド、劇団の配役＝DI、銀行振込＝トランザクション、秘書＝プロキシ、傘立て＝コネクションプール、伝票番号＝冪等性キー、ラジオ＝SSE、レジのカゴ＝永続コンテキスト など）
- 上記と別の例えを使うときは、その章の中だけで完結させる。

## 6. 禁止事項

- 特定の実在サービスを題材にしない。
- 説明のない専門用語。
- コピペで動かないコード（import不足、存在しないAPI、古いバージョンのAPI）。
- 「〜については後で説明します」の多用（使う場合はリンク付きで章を明示）。
- 長い前置き。最初の3行で「この章で何ができるようになるか」を示す。
