# 第5部 再送・期限・定期処理

![第5部の扉絵：再送・期限・定期処理](../assets/illustrations/part05.webp)

第4部で、QuickVote は**同時に来るリクエスト**に耐えるようになりました。この部では、時間の向きを変えて、**同じリクエストがもう一度来る**こと、**時間が過ぎる**こと、**誰も呼んでいないのに動く処理**を扱います。

ネットワークは、応答を落とします。クライアントは、再送します。時計は進み、期限は過ぎます。掃除のジョブは、途中で失敗し、2台で同時に走ります。どれも、ユーザーが操作していない場所で起きるので、**テストで再現できる形に落としておかないと、本番で初めて見つかります。**

## この部でできるようになること

- 「保存は成功したのに、応答だけが消えた」状況を再現し、再送が二重登録になる理由を説明できる
- `Idempotency-Key` の仕組み（訪問者 × キー、リクエストのハッシュ、同一トランザクション、保持期限）を、コードとSQLで説明できる
- 「exactly once」と言わずに、冪等性が何を保証し、何を保証しないかを言い切れる
- 締切の境界（直前・ちょうど・直後）と、判定に使う時刻（ロックを取った後）を決め、`Clock` を注入したテストで固定できる
- 「期限切れの拒否」と「物理削除」を分ける理由を説明できる
- 定期処理を、件数を区切り、途中失敗から続きから動き、2台でも1台だけが動く形に設計できる
- `@Scheduled` のスレッド数、`@Async` とトランザクション、例外ログの機密という、定期処理の落とし穴を指摘できる

## アプリの到達状態

第4部までの QuickVote は、人数上限・選択肢上限・1人1票が同時実行でも守られていました。この部で、次の約束が加わります。

| 約束 | 守る仕組み | 確認するテスト |
| --- | --- | --- |
| 再送しても二重登録しない | `Idempotency-Key` ＋ 同一トランザクションの記録 | `IdempotencyIT`、`IdempotencyRaceIT` |
| 締切後は投票・追加・参加・招待受諾を拒否 | 締切判定（ロック後の `Clock`）、半開区間 | `DeadlineIT` |
| 作成から7日で物理削除 | `@Scheduled` ＋ 件数の区切り ＋ アドバイザリロック | `CleanupIT` |
| 定期処理の失敗が機密を漏らさない | `SafeThrowable`（許可リスト方式） | `LoggingIT` |

## 実験コードの置き場

この部の実験は、リファレンス実装（`code/quickvote/`）を**変更せず**、その jar を実験用 DB につないで動かします。

```text
code/labs/
├── ch27-idempotency/   compose.yaml、scenario.sh（応答が消える事故）、concurrent.sh、two-sessions.sh、put-and-expiry.sh
├── ch28-time-expiry/   compose.yaml、scenario.sh（ロック待ちと締切）、StaleNow.java（判定時刻の模型）
└── ch29-scheduling/    compose.yaml、failure-resume.sh、two-instances.sh、advisory-lock.sh、async-lab/（@Scheduled と @Async の実験）
```

DB は `docker compose up -d`（ホスト側ポートは 25427／25428／25429）。実験が終わったら `docker compose down -v` で片付けます。

## 第5部のチェックリスト

各項目に、**白紙に自分の言葉で書いて説明できたとき**に ✅ を付けます。目安は「③ 検証できる」です。

- [ ] 応答が消えたときに、クライアントが「届かなかった」「失敗した」「成功した」を区別できない理由を、表で説明できる
- [ ] 再送が二重登録になる事故を、`curl --max-time` とDBのトリガーで再現できる
- [ ] 冪等性（`PUT`、UNIQUE ＋ upsert）で解ける問題と、`Idempotency-Key` が必要な問題を分けられる
- [ ] `Idempotency-Key` のスコープを「訪問者 × キー」にする理由を、情報漏えいの観点でも説明できる
- [ ] 同じキーで同じ内容・違う内容・同時に来た場合の3つの動きを、`ON CONFLICT DO NOTHING` の待ちを含めて説明できる
- [ ] 業務更新と冪等性の記録を同じトランザクションに置く理由を、「別トランザクションだと何が壊れるか」で説明できる
- [ ] 「exactly once」と言わずに、保持期限内・同じ訪問者・同じキーという保証の範囲を言い切れる
- [ ] 「INSERT が 0 件だった」の後で記録が消えている競合を、`FOR SHARE` と先取りのやり直しで直す理由を説明できる
- [ ] 締切の境界を半開区間と決め、直前・ちょうど・直後のテストを `Clock` を進めて書ける
- [ ] 締切の判定時刻を「ロックを取った後」に読む理由を、ロック待ちの実験で示せる
- [ ] 締切を絶対時刻でなく「何分後か」で受け取る理由を、時計のずれと通信時間で説明できる
- [ ] 「期限切れの拒否」と「物理削除」を分ける理由を3つ挙げられる
- [ ] 定期削除を、件数の区切り・1バッチ1トランザクション・条件を状態で書くことで、途中失敗から続けられる形にできる
- [ ] 2台で `@Scheduled` が二重に動く問題を、`pg_try_advisory_lock` で1台に絞る仕組みと落とし穴（unlock、接続の占有）を含めて説明できる
- [ ] `@Async` が呼び出し元のトランザクションの外で動くことと、例外ログに機密が出る理由（`SafeThrowable`）を説明できる

## 統合課題：事故対応ドリル

次の3つの報告を受けたと仮定して、**ログとSQLだけで原因を絞る手順**を、白紙に書いてください。

1. 「同じ選択肢が2つ登録されている。ボタンは1回しか押していない」
2. 「締切を過ぎたあとに、得票数が1つ増えていた」
3. 「期限切れの投票が、10日たっても消えていない」

??? success "解答の例"
    **1.** 同じ訪問者の `idempotency_records` に、該当する2つの `idem_key` があるか。**キーが違うなら、クライアントがキーを毎回作り直している**（最初の事故の再現）。キーが同じで2行あるなら、保持期限（24時間）を超えた再送か、記録が定期削除で先に消えている。`created_at` と、`options.created_at` の差を見る。
    **2.** その票の `votes.voted_at` と `polls.closes_at` を比べる。`voted_at` が締切より後なら、判定が古い時刻で行われた疑い（ロックを取る前に時刻を読んでいないか）、または手動締切の `status` 更新が漏れている。時計がずれた別のインスタンスが書いた可能性もある。
    **3.** アプリのログで `ExpiredDataCleaner` の行を見る。「失敗しました」が続いているなら、SQLSTATE とスタックから原因を絞る（居座る行がないか）。「スキップします」しか出ていないなら、ロックを持ったまま残っている接続がないか `pg_locks`（`locktype='advisory'`）を確認する。何も出ていなければ、`@EnableScheduling` や設定の間隔、スケジューラのスレッドが塞がっていないかを疑う。
